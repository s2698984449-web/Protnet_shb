## 0.3 Phase 1 跨域 Few-shot 元训练（两个子项目公共）

### 0.3.1 数据集构造 (Task Builder)

```text
元训练输入
    │
    ↓
common/task_builder.py
    │  · FusedNWaysKShots(dataset, n=ways, k=2*shots)   选 ways 类 + 2K 样b/类
    │  · LoadData(dataset)                                读入 RGB 与可选多模态
    │  · RemapLabels(dataset)                            重标为 0…(N-1)
    │  · ConsecutiveLabels(dataset)                       连续编号
    │
    ↓
learn2learn Taskset[以 domain 为单位]
    │  · train_tasksets 选自 domain_0..2 (航空) 或 domain_0 (车潩)
    │  · test_taskset   选自 domain_3 (完全 holdout)
    │
    ↓
一个 Episode (N-way K-shot)
    │  ├─ Support set: N × K 个有标样本 (适应集)
    │  └─ Query set:   N × K 个有标样本 (评估集)
```

> **为什么用 learn2learn**：它是 PyTorch 原生 Few-shot 库，提供标准的 N-way K-shot 构造、Taskset 缓存、随机采样。我们谁都不重写这部分代码。

输入   (RGB 256×256×3) | (Thermal 320×240×1) | (Ultrasonic 512 × 1)

                    │                          │                       │

                                       │
                                       ↓

### 0.3.4 多模态融合 + 任务编码 (Fusion + Task Encoding)

```text
                                domain meta (AL7075 / 任意工艺参数)
                                                    │
                                                    ↓
                                         TaskEncoder(task_encoder.py)
                                         · material_net    (12 → 32)
                                         · process_net     (8  → 16)
                                         · history_net     (10 → 16)
                                         · fusion Linear(64 → 64)
                                                    │
                                                    ↓
                                                任务嵌入 τ (64-d)

(f_rgb, f_th, f_us, τ) 传入 AsymmetricFusion (fusion.py)
    │  · 各路独立分类头 cls_i: Linear(128 → num_ways)
    │  · 保证度 conf = softmax(max(logits))
    │  · 动态权重 w = softmax(β·conf + α·kb_prior + γ·τ)
    │  · 输出 logits = Σ_i w_i · logits_i
    │
    ↓
    最终分类输出 (受任务先验与任务嵌入同时调节)
```

### 0.3.5 车潩主线：ProtoNet 头 (Metric Learning, 无内环)

```text
common/protonet_loop.py
    │
    │  build_prototypes(support_emb, support_labels, ways)
    │  ├─ Mean pooling       — 简单平均
    │  ├─ Trim-mean pooling   — exp14 (去除最高/最低 10%)
    │  └─ Mean Shift          — 多个聚类中心
    │
    │  MahalanobisHead(警告距离头)
    │  └─ 每类可学习的方差 log_vars → 加权距离
    │
    │  evaluate_protonet_query(model, support, query)
    │  ├─ 计算 prototypes  (support)
    │  ├─ 计算距离矩阵 (query × prototypes)
    │  └─ logits = -dist → cross_entropy(logits, query_labels)
    │
    │  距离选项: Euclidean / Cosine / Mahalanobis
    │
    ↓
    外环二阶段更新 (不需内环，原始 ProtoNet)：
    │  · backbone 参数: Adam, backbone_meta_lr = 1e-5   (exp14 验证)
    │  · 头/head 参数:  Adam, head_meta_lr    = 1e-3
```

### 0.3.6 航空主线：MAML 头 + Stop 头 + 三阶段课程

```text
common/maml_loop.py
    │
    │  maml_origin.clone(model)
    │    └─ 复制 初始参数 θ → fast_weights
    │
    │  内环 adapt_steps 次:
    │    for _ in range(adapt_steps):     # 默认 5 步
    │        loss = CE(learner(support), support_labels)
    │        fast_weights = θ - α · grad(loss, adapt_params)
    │      # adapt_params = fusion + projection (冻结 backbone 时)
    │      # adapt_params = fusion + projection + backbone (不冻结时)
    │
    │  外环 (只在 query 集上一次)：
    │    logits = learner(query, fast_weights)
    │    supervised_loss = CE(logits, query_labels)
    │    rl_loss         = Stop 头 RL (可选)
    │    meta_loss = supervised_loss + w_rl · rl_loss
    │    meta_loss.backward() → 外环 optimizer 更新 θ
    │
    │  三阶段课程 (参数在 train.py 默认)：
    │    ├─ Stage 1 (iter 0–100):      w_rl=0       仅监督
    │    ├─ Stage 2 (iter 100–200):    w_rl=0→0.3 逐渐加 RL
    │    └─ Stage 3 (iter 200–iters):  w_rl=0.5     adapt_steps 减 2
    │
    ↓
    元训练主循环 (maml_train.py)
    │  for iter in range(iters):
    │    · 从 train_tasksets 随机抽 domain + 抽 meta_batch_size 个 task
    │    · 内外环更新（如上）
    │    · 每 50 iter 在 test_taskset 上评测 50 task
    │    · 如果该次评测击破 best → 保存 *best.pt
```

        ↓

        ↓

### 对本研究最重要的判断

单纯：

> Industrial Defect + Few-shot

已经不是很强的创新空间。

更值得研究的是：

> **Industrial Defect + Few-shot + Multi-condition + Cross-component + Domain Generalization**

尤其值得关注：

> **如何从少量跨工况/跨构件数据中分离 condition-specific information、component-specific information 与 defect-invariant information。**

这里三个英文术语的中文解释：

| 英文术语 | 中文含义 | 在我们项目中的具体所指 | 为什么需要分离 |
|---|---|---|---|
| **condition-specific information** | 工况特有信息 / 成像条件相关信息 | 描述“这张图是怎么拍出来的”——包括光照强度 / 方向、相机曝光、白平衡、传感器噪声、偏振角、反射率等 | 如果模型把“反光强度”当成“缺陷特征”学进去，**遇到不同光照就会失效**。我们的目标是让模型忽略这些信息 |
| **component-specific information** | 构件特有信息 / 物体几何与材质相关信息 | 描述“这是哪个零件”——包括表面曲率、纹理、材质（金属 / 塑料 / 漆面）、位置、几何形状 | 不同构件（车门 vs 引擎盖）的“正常外观”差异很大。如果模型把“车门曲线”当成“缺陷”学进去，**换到引擎盖就会误判**。我们的目标是让模型忽略这些信息 |
| **defect-invariant information** | 缺陷不变信息 / 与缺陷本质相关的信息 | 描述“这是什么缺陷”——包括划痕形状、麻点尺寸、凹陷深度、橘皮程度、异色区域等 | 这是**唯一应该保留**的信息。无论在什么工况下、什么构件上，**同一种缺陷应该具有相似的表征**。我们的最终目标就是学到这个不变表征 |

**三者关系的图示：**

```text
                输入图像 (x)
                    │
                    ↓
            Backbone 编码 (f)
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
   condition    component     defect
   feature      feature       feature
       │            │            │
       ↓            ↓            ↓
       ✕            ✕            ✓
   应该抑制      应该抑制      应该保留
   (repress)    (repress)    (preserve)
       │            │            │
       └────────────┴────────────┘
                    ↓
              Defect-invariant
              Representation
                    │
                    ↓
             Few-shot Detection
```

**对我们的意义：** 这三个分离目标构成了 CMPL 的科学问题 —— “如何**显式**地把 condition-specific 和 component-specific 信息从 backbone 输出中剥离，只保留 defect-invariant 部分用于 Few-shot Detection”。这是 CMPL 区别于普通 ProtoNet 的根本点。ProtoNet 把所有信息混在一起；CMPL 强制做解耦（disentanglement）。

这与“高光漆面 + 跨构件 + RGB/偏振 + CMPL”高度匹配。

## 1bis.3 为什么要这样设计？说力源源

1. **可继承性** —— 现有 exp07–exp16 所有检验点都保留，原有 module 不受影响。只要在原架构外加上"【NEW】"的部件就能上报增量增益。

3. **可对标性** —— 所有【NEW】部件都能追溯到 12 篇文献，证明"我们不是亲手造轮子，而是在论文社区里被验证过的技术"。这点对于论文提交、特别是审稿人反问"你的创新点 vs R²-Net 有什么不同？"时是重要依据。
4. **可报告性** —— 每个 **红色** 部件都有明确的**外部可对比 baseline**（参考其他论文代码库）。"加上 Condition Encoder 之后从 95% 到 96.5%"这种描述有实验支撑。这不是谜题，是可验证的。

## 1bis.3.5 用户视角的 CMPL 架构图与三大质疑

> **本节由使用者提出三个问题引发**：

> 1. 上面画的架构里“没有用到 Patch Match”，是否遗漏？
> 2. backbone 是 YOLO——“没有一定的通用特征”，只是依赖预训练，是否能保证“通用方法”这个承诺？
> 3. 架构中“Condition-aware Feature 反过来调节 backbone”以及“backbone 同时被 Condition 分支调节”，这种两路同时作用的设计是否重复？

### B. 三大质疑的诚实回答

#### 质疑 1：“架构里没用到 Patch Match”是否遗漏？

**不遗漏，但仓库里已隐含“Patch-level matching 原型”**。
- **我们现在的 ProtoNet 实际上就是Patch-level matching的最简版本**：`build_prototypes()` 在 support 集的 256×256 全图上计算 128-d 全局特征，然后用 query 的 128-d 全局特征与 prototype 计算距离矩阵。本质上是把“全图”当作一个“patch”，跨全图走 prototype matching。
- **Patch Matching 论文（P3, 2024）的真正价值**：不是"换个算法"，而是"换个问题粒度"——从"这张图有没有缺陷"切换到"图的哪个位置有缺陷"。我们这个架构里依然可以接上“Multi-scale spatial map”（backbone 输出 (B, 128, h', w')），计算“每个位置与 prototype 的距离”，就是 Patch Matching。
- **论文跟踪表【NEW】**：在 `common/protonet_loop.py` 中加入 `build_patch_prototypes()`（从 backbone spatial map 拆 patch，每个 patch 独立起 prototype），再接 `evaluate_patch_query()`（计算 pixel-level distance map）。这是"阅读路线"里 0.3.3 的 `Multi-scale spatial map` 的直接升级路径。

#### 质疑 2：“backbone 是 YOLO——有没有通用特征？

**诚实答案：“输入部分”是通用的，“中间表征”不一定。需要明确区分三个层次：
- 第一层：**输入**较通用。yolo26n.pt 是 ultralytics 在 COCO 上训练的——包含 80 类常见物体（人、车、猫狗、植物、家具……）的全局保障。但 COCO 不包含企业级“划痕、麻点、凹陷”等微细缺陷。所以"骨架在 COCO 上训练"这个事实本身**不为你的企业缺陷任务提供“企业级”的“通用特征”。
- 第二层：**中间表征**。需要仔细看中间表征。主导思路是"pretrained backbone 是起点而不是终点"。你提到的“取决于预训练”这个说法是正确的，但**起点的质量决定了上限**。项目中车潩预训练使用 cmpl_yolo26_supcon_v9.pt（车潩 5 任务自监督），代替 yolo26n.pt，从 0.834 提到 0.848。但这些预训练仍然是“车潩专业”的，跨到航空会丢 22 个百分点。
- 第三层：**预训练是否可以"通用"**？这个问题走到了领域边界。现在三个可能的路径：
  - A.**选型×预训练×元训练三者解耦**：骨架可以是任何适用于该场景的（YOLO 也好、DINOv2 也好、CLIP 也好），只要接入 CMPL 的三分支解耦流程就能上报增量增益。这是架构层面的“通用”——backbone 不变，接入方式变。
  - B.**预训练本身"跨域"**：越是开源 Foundation Model（DINOv2 、 SAM、 CLIP）越能保证“输入端”的通用性。本项目现在是 yolo26n.pt 加 cmpl 预训练，未来切到 DINOv2 是一个可行方向。
  - C.**跨业务"资源间依赖"**：车潩×航空两个预训练同时依赖不是一个“通用方法”。但架构本身“骨架可以是任何”这一点以后能提供一个“选型上的通用方法”：“任何 backbone + CMPL 三分支解耦”都是可行的一个宽口。

#### 质疑 3：“Condition-aware 反向调节 backbone + backbone 同时被 Condition 分支调节”是否重复？

**是重复了，但可以拆成两个独立机制**。原图里有两条 Condition 到 backbone 的作用路径：
1. **Condition → Condition-aware Feature → × backbone 输出**：这是“attention gate”，用 Condition 信息为骨架输出加权。适合 fine-grained 个体 (例如 CBAM × backbone)。
2. **Condition → 独立走出 Condition-aware Feature → 与 backbone 输出作减法**：这是“orthogonal projection”，用 Condition 信息在 backbone 表征空间里剥离 Condition 方向。适合 defect-invariant feature 训练。

两条路径可以同时使用，但权重不能同时变高——一般只选其中一个：
- 仅用 attention gate（轻量）：适合 backbone 可训练、预训练质量较低、快速调优。
- 仅用 orthogonal projection（重量）：适合 backbone 冻结、预训练质量高、需要 explicit condition-invariant 特征。
- 两者交替使用（中量）：attention gate 控 backbone 输出的 fine-grained 分量，orthogonal projection 控低频外部信息，双双驱动。适合"高光漆面"这种"可见光大为主"的场景。

### C. 总结：用户架构 vs 原架构的主要区别

| 要点 | 用户架构中的设计 | 原 1bis 架构中的对应 | 说明 |
|---|---|---|---|
| Multi-condition 输入 | 起始入口：Multi-condition 输入 | 输入口未区分条件 | 用户架构明确说“同一 defect 在不同条件”，这正是本项目的 condition 与众不同的地方 |
| Condition Encoder × backbone 交互 | × (乘口) | 原架构中位于 backbone 之后 | 用户架构将交互提前，这是 valid 的选型 |
| Component Encoder 独立路径 | 独立走 backbone 后 | 原架构也是 shared subspace 后 | 一致 |
| Patch Matching | 未明确出现 | 隐含于 ProtoNet （全图 = 1 patch），spatial map 可升级为明确 Patch Matching | 用户架构遗漏了明示 Patch Matching，需补 |
| Adaptive Prototype (cross-attn) | 现有 | [P7] 提到 | 一致 |
| Defect Detection 输出 | 类别 + 置信度 | 仅类别 | 用户架构多了"置信度"（ calibration），这是实际部署的要求 |

### D. 面对质疑的项目如何重新定位

1. **保留“通用方法”这个承诺但重新定义**：“通用”不是“不需要预训练才算通用”，而是“预训练本身可以被换成 foundation model，架构本身仍可迁移。为了“通用”这一点，CMPL 可以 backbone-agnostic：只要换 backbone 就是一个 new paper。
2. **保证架构层"三分支"在多种 backbone 上都能站住**：接下来要写DINOv2-CBAM-Condition-Component-ProtoNet（全foundation）与YOLO26-SupCon-Condition-Component-ProtoNet（项目现状）的对比实验。这个对比**说明 CMPL 是“骨架中立”的机制**。
3. **补上Patch Matching 代码跳路径**：在protonet_loop.py 中加入 `build_patch_prototypes`（从 spatial map 拆 patch），计算 pixel-level 预测图，这是未来补“置信度”后的下一步。
4. **中期交付物**：本论文“CMPL”中必须明确写“其中什么不依赖具体 backbone”，仅仅什么“依赖”。这是审稿人问“你的方法能不能换 backbone”时的结论。

# 3. 论文一：Few-shot defect recognition for the multi-domain industry

## 3.1 基本信息

**题目：** Few-shot defect recognition for the multi-domain industry via attention embedding and fine-grained feature enhancement

**年份：** 2024

**期刊：** Knowledge-Based Systems

**论文链接：**

https://www.sciencedirect.com/science/article/pii/S0950705123010146

## 3.2 研究问题

论文直接面向：

- Multi-domain industrial defect recognition
- Few-shot learning
- 多类别工业缺陷
- 标注成本高
- 新缺陷样本少

核心问题：

```text
多个工业领域
      ↓
不同产品/不同域
      ↓
每个新缺陷只有少量样本
      ↓
如何获得可靠缺陷表示？
```

## 3.3 方法

核心可以概括为：

```text
Input                              ← 输入：工业缺陷图像（可能含强反光、油污、纹理噪声）
 ↓
Backbone                           ← 骨干网络：常用 ResNet / ConvNet，提取通用视觉特征
 ↓
Attention Embedding                ← 注意力嵌入：让特征图在空间 / 通道维度上重新加权
 ↓                                   使模型自动“看向”具有判别性的像素
Fine-grained Feature Enhancement   ← 细粒度特征增强：把每个像素 → 局部区域 → 细粒度缺陷特征
 ↓                                   抑制背景、材质、构件等无关信息
Multi-grained Feature Fusion       ← 多粒度特征融合：把不同尺度 / 不同抽象层级的特征拼起来
 ↓                                   既保留全局上下文，也保留局部细节
Few-shot Recognition               ← 小样本识别：用 prototype / metric learning 在少量样本下完成分类
```

### 各模块中文解释与对我们的启示

| 模块 | 中文含义 | 在工业缺陷中的作用 | 对 CMPL 的启示 |
|---|---|---|---|
| **Input** | 输入图像 | 工业现场采集的含缺陷图像 | 我们项目中的 RGB + 偏振四通道图像也是 Input 的一种扩展 |
| **Backbone** | 骨干网络 | 提取通用视觉特征；通常冻结或微调 | 我们使用 YOLO26 backbone（exp14 中 `backbone_meta_lr=1e-5`）已经验证了「不冻结 backbone 但小学习率」的可行性 |
| **Attention Embedding** | 注意力嵌入 | 让网络自动聚焦到 defect 区域，抑制无关背景 | 高光漆面中缺陷常常被强反射淹没，**注意力机制特别值得借鉴** —— 我们可以把它作为 Condition-aware 通道的第一个具体实现 |
| **Fine-grained Feature Enhancement** | 细粒度特征增强 | 把粗粒度的"图像级特征"分解到"区域级 / 像素级特征" | 这是论文一的核心精神：**Prototype 不应该只代表图像，应该代表 defect region** —— 与我们"Component vs Defect 解耦"的思路完全一致 |
| **Multi-grained Feature Fusion** | 多粒度特征融合 | 把深层语义特征 + 浅层纹理细节结合 | 可以作为我们后续**消融实验 Level E (Fine-grained)** 的对应物 |
| **Few-shot Recognition** | 小样本识别 | 用 prototype / metric learning 分类 | 这正是我们当前 ProtoNet + Trim-mean + Mahalanobis 范式 |

### 可以借鉴的地方

1. **Attention Embedding 模块**：目前 CMPL 的 backbone (YOLO26) 输出是 128 维全局特征，对缺陷位置不敏感。可以在 backbone 后接一个 CBAM / SE 注意力层（参数量小、易训练），提升对漆面划痕、麻点等小目标的敏感度。
   - **理由**：exp10 (protonet + CBAM) 已经在航空数据上验证了 CBAM 的有效性（test acc 100%，但样本量小）。在工业漆面数据集上做更严格的 N-way K-shot 验证是有意义的。

2. **Fine-grained Feature Enhancement 模块**：当前我们直接用 `model.encode(x)` 得到 128-d 全局向量。论文一提示我们可以**拆出 patch-level / region-level 特征**，再做 prototype。
   - **理由**：高光漆面缺陷（如划痕、麻点）面积可能只占整图 0.1% 以下，全局平均会被背景淹没。把 backbone 输出 reshape 成 `(B, C, H', W')`，再做 spatial-aware pooling（如 trim-mean + 最大值 + attention 加权），能更好突出 defect。

3. **Multi-grained Feature Fusion**：YOLO26 backbone 通常有多尺度输出（P3 / P4 / P5）。当前 CMPL 只用了最后一层。可以在 prototype 计算前加入多尺度融合，类似 FPN 结构。
   - **理由**：大尺度缺陷（如掉漆、刮擦）和微缺陷（如橘皮、麻点）需要不同感受野。多粒度融合可同时覆盖。

### 可以插入的地方（在我们代码中的具体位置）

```text
我们的项目结构
─────────────────
common/backbones.py              ← ① Attention Embedding 可插入这里
                                     (在 YOLO26 编码后接 CBAM/SE 模块)

common/multimodal_model.py       ← ② Fine-grained Enhancement 改造点
                                     (把 128-d vector 拆为 region-level features)

common/protonet_loop.py          ← ③ Multi-grained Fusion 改造点
   build_prototypes()
                                     (在 prototype 池化前融合多尺度特征)
```

**理由总结**：论文一虽然发表在 2024，但它提出的"输入 → 骨干 → 注意力 → 细粒度增强 → 多粒度融合 → 小样本识别"是**通用范式**，与我们 CMPL 的核心思想（把 defect 从 component / condition 中分离）天然契合。它不直接给我们算法，但给我们提供了**模块化拆解的视角**，让我们的改造有迹可循。

## 3.4 论文真正值得借鉴的点

工业缺陷中：

```text
Image
=
Defect
+
Material
+
Background
+
Lighting
+
Component
```

如果直接学习 image-level representation，很容易把：

```text
工况特征
+
构件特征
+
缺陷特征
```

混合。

因此 Fine-grained Representation 很重要。

## 3.5 对 CMPL 的启发

目前可以认为：

```text
Prototype
≈
Defect + Component + Condition
```

更合理的目标应该是：

```text
Defect Prototype
≈
Defect-invariant representation
```

而：

```text
Component
Condition
```

应该显式建模。

# 5. 论文三：Patch Matching for Few-Shot Industrial Defect Detection

## 5.1 基本信息

**年份：** 2024

**方向：**

> Patch-level Few-shot + Memory Bank

**论文：**

https://openreview.net/forum?id=vBzEeHmH1b

## 5.2 核心思路

不是简单：

```text
Image
 ↓
Global Feature
 ↓
Prototype
```

而是：

```text
Image                              ← 输入：原始工业图像（如 1920×1080 高分辨率漆面图）
 ↓
Patch Extraction                   ← Patch 切块：把图像切成 N×N 的小方块（如 64×64 或 128×128）
 ↓                                   每个 patch 可能包含纯背景、纯缺陷、或缺陷边缘
Patch Feature                      ← Patch 特征提取：用 backbone 把每个 patch 编码成 D 维向量
 ↓                                   此时每个 patch 都有独立表征，不再被全局平均稀释
Memory Bank                        ← 记忆库：把 support 中所有 patch 特征存入一个可检索的库
 ↓                                   通常用 FAISS / 简单矩阵做近似最近邻（ANN）查找
Patch Matching                     ← Patch 匹配：query patch 与 bank 中所有 patch 计算距离
 ↓                                   取最近邻或 top-K 近邻，统计得分
Defect Localization                ← 缺陷定位：根据每个 query patch 的得分图，得到缺陷空间位置
 ↓                                   输出 heatmap 或像素级 mask
```

### 各步骤中文解释与对我们的启示

| 步骤 | 中文含义 | 在工业缺陷中的作用 | 对 CMPL 的启示 |
|---|---|---|---|
| **Image** | 原始图像 | 高分辨率工业图（漆面/芯片/PCB） | 我们 `multimodal_model.py` 中的 `x_rgb` 是 backbone 的输入，与此对应 |
| **Patch Extraction** | Patch 切块 | 解决"缺陷小、图大"的核心：把粒度从 image 降到 region | 高光漆面划痕只占几十像素，必须降到 patch 级才能精确定位 |
| **Patch Feature** | Patch 特征 | 每个 patch 独立表征，避免全局平均稀释 | 这与论文一 Fine-grained Enhancement 同源 |
| **Memory Bank** | 记忆库 | 把 support 信息结构化存储，支持 O(1) 检索 | 我们的 prototype 库（`build_prototypes()`）就是一种最简单的 memory bank —— 取各类中心作为"压缩的 bank" |
| **Patch Matching** | Patch 匹配 | 在 bank 中查找最近邻 / top-K | 我们的 `evaluate_protonet_query` 用的就是"距离度量 + argmin"的最简单匹配 |
| **Defect Localization** | 缺陷定位 | 输出像素级 / 区域级 mask | 当前 CMPL 只做 **classification**，不输出空间位置；这是未来扩展方向 |

### 可以借鉴的地方

1. **Patch-level prototype**：当前我们用 `build_prototypes(support_emb, ...)` 在全局 128-d 特征上算均值 / trim-mean。可以改造为：先把 backbone 输出 reshape 成 `(B, C, H', W')`，然后**对每个 spatial cell 单独算 prototype**。
   - **理由**：高光漆面 defect crop 通常是 defect 区域 + 一圈正常漆面，全局平均会"稀释" defect 信号；patch-level prototype 更接近真实 defect 表征。

2. **Memory Bank 思路**：我们可以为每个 component / condition 维护一个**正常样本 bank**，推理时 query feature 与 bank 的距离作为 anomaly score。
   - **理由**：这对应 RadioCore 论文的 training-free 思路（论文九），可以在不重训 backbone 的情况下处理新工况。

### 可以插入的地方（在我们代码中的具体位置）

```text
common/protonet_loop.py
   build_prototypes()               ← ① 改造为 patch-level prototype
                                       (输入从 (N, D) 改为 (N, C, H', W'))

common/protonet_loop.py
   evaluate_protonet_query()        ← ② 在距离计算时支持 patch-bank KNN
                                       (类比 Patch Matching)

common/multimodal_model.py          ← ③ backbone 输出改造点
   model.encode()                     (增加 spatial output，不只返回 pooled vector)
```

**理由总结**：Patch Matching 给我们的最大启示不是算法，而是**问题粒度的切换**——从"这张图有没有缺陷"切换到"图的哪个位置有缺陷"。这对我们漆面项目特别重要，因为甲方不仅要知道"有没有"，更要知道"在哪、要修多大面积"。当前 CMPL 还停留在 classification 阶段，但论文五（七）的 Few-shot Defect Segmentation 提示我们，可以把任务升级到 **segmentation**。

## 5.3 为什么适合工业缺陷

工业缺陷通常是：

```text
整图很大
+
缺陷区域很小
```

例如：

```text
┌──────────────────────┐
│                      │
│       ┌───┐          │
│       │缺陷│          │
│       └───┘          │
│                      │
└──────────────────────┘
```

Global Feature 很容易被：

- 背景
- 构件
- 材质
- 光照

淹没。

Patch-level matching 可以提高局部缺陷的权重。

## 5.4 对 CMPL 的启发

可以考虑：

```text
Support Image
     ↓
Patch Features
     ↓
Fine-grained Prototype
     ↓
Query Patch
     ↓
Prototype Matching
```

即：

> 从 Image Prototype 进一步走向 Region/Patch Prototype。

# 8. 论文六：NexViTAD

## 8.1 基本信息

**题目：** NexViTAD: Few-shot Unsupervised Cross-Domain Defect Detection via Vision Foundation Models and Multi-Task Learning

**年份：** 2025

**论文：**

https://arxiv.org/abs/2507.07579

## 8.2 核心架构

```text
Hiera                              ← Vision Foundation Model：Meta 提出的分层 ViT
+                                  ← Hiera 擅长多尺度；DINOv2 擅长通用语义
DINOv2                              二者特征拼起来作为 backbone 的等价替代
      ↓
Hierarchical Adapter               ← 分层适配器：轻量瓶颈层（如 MLP+残差），把 foundation 特征适配到工业数据
      ↓                            冻结 Hiera/DINOv2 主干，只训练 Adapter（约几 % 的参数）
Shared Subspace Projection         ← 共享子空间投影：把所有 domain 特征投影到一个共同子空间
      ↓                            在该子空间中，domain-specific 信息被压缩，defect 信息被保留
Multi-task Decoder                 ← 多任务解码器：同时做分类 + 定位 + 分割
      ↓                            多任务约束迫使 shared subspace 学到"任务相关"而非"域相关"特征
Anomaly Detection                  ← 异常检测：最终输出 anomaly map / score
```

### 各模块中文解释与对我们的启示

| 模块 | 中文含义 | 在工业缺陷中的作用 | 对 CMPL 的启示 |
|---|---|---|---|
| **Hiera + DINOv2** | 双 Foundation Model | 用大型预训练替代从零训练 backbone | 我们当前用的是 YOLO26 backbone，效果不错（exp14 = 98.1%）。但如果未来想"训练数据更少"或"新产品更快导入"，可以换 DINOv2 |
| **Hierarchical Adapter** | 分层适配器 | 轻量微调，避免破坏 foundation 已有知识 | 这是 LoRA-style 思路。我们 YOLO26 unfreeze (lr=1e-5) 已有类似效果，但 Adapter 更系统化 |
| **Shared Subspace Projection** | 共享子空间投影 | **核心模块**：把多 domain 特征压到共同子空间 | 这正是 **CMPL Condition Branch + Component Branch → Defect-invariant** 的几何动机 |
| **Multi-task Decoder** | 多任务解码 | 共享子空间的稳定性用多任务约束 | 我们可以做 "Classification + Anomaly Score" 双任务，互相正则化 |
| **Anomaly Detection** | 异常检测 | 最终输出 | 当前 CMPL 是 closed-set classification，可以扩展为 open-set anomaly detection |

### 可以借鉴的地方

1. **Shared Subspace Projection 是 NexViTAD 的灵魂**：把所有域的特征 `f_d` 投影到子空间 `P(f_d)`，使得 `P(f_A) ≈ P(f_B) ≈ P(f_C)`，但只在 defect-relevant 维度上接近。
   - **理由**：这正是我们 CMPL "Condition Encoder + Component Encoder + Defect Prototype" 想要达到的目标。我们可以把它形式化为一个 `subspace_projection(x) = W_condition·x + W_component·x` 的解耦表示。

2. **Multi-task Decoder 的正则化效应**：classification 之外再加一个 task（如 defect 像素级重建），迫使 backbone 学到更稳定的 defect 表征。
   - **理由**：高光漆面的 defect 在 support 集里可能只有 5 张图，classification 监督信号太弱；自监督重建可以补足。

### 可以插入的地方（在我们代码中的具体位置）

```text
common/backbones.py                 ← ① 可选：把 YOLO26 替换为 DINOv2 + Adapter
                                       (Adapter 就是 nn.Sequential(Linear→ReLU→Linear))

common/multimodal_model.py          ← ② 核心：新增 subspace projection 模块
   new class SubspaceProjection()    (在 backbone 输出后接 W_cond + W_comp 解耦)

common/maml_train.py                ← ③ 训练时增加辅助 task
   train()                           (如：除 classification loss 外加 reconstruction loss)
```

**理由总结**：NexViTAD 与我们的 CMPL 哲学非常接近 —— 都认为"domain-specific 信息是噪声"。区别在于 NexViTAD 用 foundation + 投影实现，我们用 CMPL 用 prototype + condition/component 解耦实现。可以把 NexViTAD 的 Subspace Projection 作为 **CMPL 的数学形式化基线**（即 CMPL 解耦的目标函数在最优解下 ≈ NexViTAD 的 subspace）。这是一个很好的理论联系点。

## 8.3 最值得研究的模块

### Shared Subspace Projection

目标：

```text
Domain A
Domain B
Domain C
      ↓
Shared Feature Space
```

使：

```text
Domain-specific Information
```

降低，同时保留：

```text
Defect-related Information
```

## 8.4 对你的直接启发

你的模型可以进一步思考：

```text
Condition-specific feature
        ↓
Condition branch

Component-specific feature
        ↓
Component branch

Defect-invariant feature
        ↓
Prototype branch
```

这比单纯把 component 信息拼到 prototype 中更有研究价值。

# 9. 论文七：Enhancing feature interaction for improved generalization in few-shot metal surface defect segmentation

## 9.1 基本信息

**年份：** 2025

**期刊：** Knowledge-Based Systems

**论文：**

https://www.sciencedirect.com/science/article/pii/S0950705125016454

## 9.2 核心问题

目标：

```text
Few-shot
+
Metal Surface
+
Unseen Defect
+
Generalization
```

提出：

> EFINet

重点不是简单增加 backbone，而是：

> Feature Interaction

## 9.3 核心机制

```text
Support Feature                    ← 支持集特征：K 张同类别 defect 图编码后的特征向量
       ↕                           ↕ 表示双向信息流动（不是单向 concat）
Feature Interaction               ← 特征交互：support 与 query 互相"交换信息"
       ↕                           典型实现：cross-attention（Q←query, K/V←support）
Query Feature                      查询特征：从待测图像编码得到的特征
       ↓
Defect Segmentation                缺陷分割：像素级 mask
```

### 中文解释与对我们的启示

| 模块 | 中文含义 | 在工业缺陷中的作用 | 对 CMPL 的启示 |
|---|---|---|---|
| **Support Feature ↔ Feature Interaction ↔ Query Feature** | 双向特征交互 | 让 support 与 query **在匹配前就互相调整** | 当前 ProtoNet 是先各自编码 → 再算距离（无交互）。EFINet 提示：**编码阶段就进行交互**能让 support 主动"找" query 的特征空间 |
| **Feature Interaction** | 特征交互模块 | 通常是 cross-attention 或 cross-correlation | 可以作为 CMPL 的"Adaptive Prototype" 模块 —— 论文原文就提到 |

### 可以借鉴的地方

1. **Cross-attention Prototype**：当前 prototype = mean(support)。可以改为：
   ```
   prototype = mean(support) + α · CrossAttn(query, support)
   ```
   即 prototype 本身根据 query 做"局部调整"。
   - **理由**：高光漆面 defect 在 support 集可能只占小区域，全局 mean prototype 包含大量"正常漆面"信号。让 prototype 主动 query-aligned，可以聚焦到 defect-relevant 维度。这正好对应第 9.4 节 "Adaptive Interaction" 的设想。

2. **Cross-correlation (ConvNet 风格)**：对 query 特征图与 support prototype 做空间相关，生成 correlation map，再做 segmentation。
   - **理由**：这是 Siamese Few-shot Segmentation 的标准做法 (e.g., CANet)。我们当前是 classification 任务，但 future work 可以借鉴这个做 segmentation。

### 可以插入的地方（在我们代码中的具体位置）

```text
common/protonet_loop.py             ← ① 在 build_prototypes 中支持 cross-attention prototype
   build_prototypes()                (新参数 use_cross_attn=True)

common/protonet_loop.py             ← ② 新增 evaluate_protonet_query_crossattn()
                                      (query 与 prototype 做 attention 后再算 logits)
```

**理由总结**：EFINet 给 CMPL 提供了一个**模块级改造方案**：prototype 不再是死的均值，而是与 query 实时交互的活体。这是 ProtoNet → Adaptive ProtoNet 的升级路径。短期成本小（只需要在 build_prototypes 里加 1 个 attention 层），但叙事价值大（论文可写"我们的 prototype 是 query-aware 的"）。

这和：

```text
Support Prototype
       ↕
Query Feature
```

本质上存在较强联系。

## 9.4 对 CMPL 的启发

Prototype 不一定应该是：

```text
Mean(Support Features)
```

还可以考虑：

```text
Support
  ↓
Prototype
  ↕
Query
  ↓
Adaptive Interaction
```

即：

> Prototype 本身可以根据 Query 进行动态校准。

## 11.1 基本信息

**题目：** RadioCore: Few-Shot Industrial Anomaly Segmentation with Multi-Scale Radio ViT Features

**年份：** 2026

**会议：** CVPR 2026 Workshop

**论文：**

https://openaccess.thecvf.com/content/CVPR2026W/VISION26/html/Ali_RadioCore_Few-Shot_Industrial_Anomaly_Segmentation_with_Multi-Scale_Radio_ViT_Features_CVPRW_2026_paper.html

## 11.2 核心思想

代表：

> Foundation Model + Training-free Few-shot

架构：

```text
Radio ViT                          ← 一种 Vision Transformer 变体（"Radio" 指多频段特征）
     ↓                              预训练于大规模通用数据集，无需在工业数据上训练
Multi-scale Patch Features         ← 多尺度 patch 特征：从 ViT 的多个 stage 抽取 token
     ↓                              每个 stage 对应不同的感受野（早期=纹理、晚期=语义）
Normal Memory Bank                 ← 正常样本记忆库：把 K 张正常样本的 patch 特征存入
     ↓                              K 通常很小（3-5 张），这就是 few-shot 的来源
KNN                                ← K-近邻：对每个 query patch，找 bank 中最近邻
     ↓                              距离作为 anomaly score
Anomaly Score                      ← 异常分数：聚合每个 query patch 的距离 → image-level score
     ↓
Pixel-level Map                    ← 像素级图：把每个 query patch 的 score 还原回空间位置
```

### 中文解释与对我们的启示

| 模块 | 中文含义 | 在工业缺陷中的作用 | 对 CMPL 的启示 |
|---|---|---|---|
| **Radio ViT** | 多频段 ViT backbone | 用 foundation model 的强表征替代专门 backbone | 我们当前 YOLO26 是目标检测专用 backbone；如果想做到 training-free，需要换 DINOv2 / Radio ViT |
| **Multi-scale Patch Features** | 多尺度 patch 特征 | 兼顾大小缺陷 | 这是经典 FPN 思想在 ViT 中的体现 |
| **Normal Memory Bank** | 正常样本库 | **只存正常样本**，不存 defect | 这是 anomaly detection 的标志性差异 —— defect 类型多样未知，只学"什么是正常" |
| **KNN** | K 近邻查找 | 简单但有效的距离度量 | 我们的 prototype + 距离本质上就是 K=1 的 KNN |
| **Anomaly Score** | 异常分数 | 距离归一化后的得分 | 可以作为 CMPL 的 auxiliary output（多任务） |
| **Pixel-level Map** | 像素级图 | 空间定位输出 | CMPL 当前只做 classification，未来可加 |

### 可以借鉴的地方

1. **Training-free 范式作为对照**：可以在我们已有的 exp14 基础上，**不重训** YOLO26，直接用 frozen backbone + KNN 做 baseline。
   - **理由**：可以作为论文的 "lower bound" baseline —— 如果 frozen backbone + KNN 都能达到 80% acc，那我们的 CMPL 改进才有意义。

2. **Normal Memory Bank 思想**：可以为每个 component（车门 / 引擎盖 / 后视镜）建立一个**正常漆面 bank**，推理时如果 query 离 bank 远 → anomaly。
   - **理由**：这是工业检测的真正业务形态 —— 客户不关心"这是 defect A 还是 defect B"，只关心"这块漆面正常吗"。我们 CMPL 当前是 closed-set classification，限制太大；Normal Memory Bank 是更普适的解。

### 可以插入的地方（在我们代码中的具体位置）

```text
common/backbones.py                 ← ① 可选：用 DINOv2 替换 YOLO26（不重训）
                                      (frozen 状态下充当 training-free baseline)

common/protonet_loop.py             ← ② 新增 evaluate_anomaly_knn()
   new function                       (query 与 Normal Bank 的距离 → anomaly score)

航空缺陷检测/scripts/                ← ③ 新增 run_anomaly_knn_baseline.py
                                      (用 frozen YOLO26 + KNN 跑 100 tasks 验证下界)
```

**理由总结**：RadioCore 给我们的最大启示是 **research 定位**：CMPL 不是唯一一个解。我们的 CMPL 必须解释清楚 **为什么 prototype learning 比 foundation + memory matching 更适合跨工况工业缺陷**。这是一个非常直接的实验对照 —— frozen backbone + KNN vs. fine-tuned backbone + CMPL。如果后者提升 > 5% ，CMPL 就有价值；如果 < 2% ，CMPL 反而显得过度设计。

## 11.3 研究趋势意义

这意味着：

> Few-shot 并不一定意味着必须进行 Meta-learning training。

现在开始出现：

```text
Foundation Model
+
Memory Bank
+
Nearest Neighbor
```

甚至 Training-free 的路线。

## 11.4 对 CMPL 的启发

CMPL 必须证明：

```text
为什么 Prototype Learning
比
Foundation Model + Memory Matching
更适合跨工况工业缺陷？
```

或者反过来：

```text
Foundation Feature
        +
Component-aware Prototype
        +
Condition-aware Calibration
```

可能成为更强的组合。

# 12. 论文十：R²-Net

## 12.1 基本信息

**题目：** R²-Net: A Hybrid Meta-Learning Framework for Cross-Domain Few-Shot Industrial Defect Detection

**年份：** 2026

**论文：**

https://www.jstage.jst.go.jp/article/jaciii/30/4/30_1138/_article/-char/en

## 12.2 核心问题

直接针对：

> Cross-Domain Few-Shot Industrial Defect Detection

即：

```text
Source Domain
      ↓
Target Domain
      ↓
Few-shot
      ↓
Industrial Defect
```

## 12.3 方法

核心结合：

  - Meta-learning
  - Relation Network
  - Reptile

本质：

```text
Support                            ← 支持集：K 张同类别 defect 图
    ↓
Meta representation                ← Meta 表征：用 Reptile 算法在 episode-level 训练 backbone
    ↓                               Reptile 是 MAML 的简化版（不用二阶导），更适合工业 Few-shot
Relation                           ← 关系网络：把 support 和 query 特征拼接后过 relation module
    ↓                               relation module 输出一个 0-1 之间的相似度分数
Query                              ← 待测样本
```

### 中文解释与对我们的启示

| 模块 | 中文含义 | 在工业缺陷中的作用 | 对 CMPL 的启示 |
|---|---|---|---|
| **Support** | 支持集 | K-shot 输入 | 与我们 ProtoNet 完全一致 |
| **Meta representation** | Meta 表征 | 用 Reptile 学习"如何快速适应" | 我们当前用 ProtoNet（metric learning）而非 Reptile；Reptile 是基于梯度的元学习，理论上更适合"快速适应新工况" |
| **Relation** | 关系模块 | 学习 support 与 query 的非线性关系 | ProtoNet 用固定距离度量（欧氏 / 余弦 / Mahalanobis），RelationNet 用可学习 MLP；后者表达力更强但需要更多数据 |
| **Query** | 待测样本 | 待分类的工业图 | 一致 |

### 可以借鉴的地方

1. **Reptile 作为 baseline**：在我们的 `maml_train.py` 中已经实现了 MAML 和 ANIL（`anil=True`），可以加一个 Reptile 实现（实现简单：每个 episode 后往 meta-weights 方向移动 α 步）。
   - **理由**：R²-Net 显示 Reptile 在跨域工业 Few-shot 上比 MAML 更稳定（因为不需要二阶导）。我们的 exp09 (Protonet) vs ANIL 已经测了不同 meta-learning 范式，但没有 Reptile。

2. **RelationNet 作为 baseline**：当前 CMPL 距离度量是固定的（mahalanobis / euclidean），可以加一个 Relation Network：用一个小 MLP 替代距离度量，学习非线性相似度。
   - **理由**：高光漆面 defect 的特征分布可能不是简单的球形（mahalanobis 假设是），RelationNet 没有这个假设。

### 可以插入的地方（在我们代码中的具体位置）

```text
common/maml_loop.py                 ← ① 新增 Reptile 训练循环
   reptile_meta_step()               (在 MAML 之外提供另一条 meta-learning 路径)

common/maml_loop.py                 ← ② 新增 Relation Network head
   RelationHead class                (输入 (s_feat, q_feat) → MLP → similarity)

航空缺陷检测/maml_train.py          ← ③ 在 train() 中支持 meta_algorithm='relation'
                                      (与 protonet, maml, anil 并列)
```

**理由总结**：R²-Net 是 2026 年最直接对标我们的工作 —— Cross-Domain Few-Shot Industrial Defect Detection。它把 Meta-learning + Relation Network + Reptile 组合在一起，是非常强的 baseline。我们的 CMPL 必须跑赢 R²-Net 才算真正有效。**强烈建议把 R²-Net 作为论文 Table 中的 "Strongest Baseline"**。

## 12.4 对你的意义

这是目前非常值得拿来做对比 baseline 的一篇。

因为你的研究也属于：

```text
Meta-learning
+
Industrial Defect
+
Few-shot
+
Cross-domain
```

因此后续实验建议至少考虑：

```text
ProtoNet
RelationNet
MAML / ANIL
Reptile
R²-Net
CMPL
```

# 13. 论文十一：Calibrated Feature Fusion

## 13.1 基本信息

**年份：** 2026

**论文：**

https://www.mdpi.com/1424-8220/26/7/2164

## 13.2 核心问题

Few-shot 中多尺度特征：

```text
Low-level                          ← 低层特征：边缘、纹理、颜色
Middle-level                       ← 中层特征：局部形状、部件
High-level                         ← 高层特征：语义、抽象类别
```

直接融合：

```text
Concat                             ← 简单拼接：把三个尺度的特征向量首尾相连
+
Fusion                             ← 融合：过一个 MLP 统一维度
```

可能产生：

> Representation Misalignment
> 表示不对齐：低层特征描述"哪里有 defect"，高层特征描述"是不是 defect"，两者空间维度不一致

## 13.3 核心思想

进行：

> Cross-stage Representation Alignment
> 跨阶段表示对齐：在融合之前，先把不同层级的特征映射到统一的 feature space

使：

```text
不同层级 feature                  ← 例如 backbone 的 stage1 / stage2 / stage3 输出
        ↓
更一致的 feature space            ← 通过 LayerNorm + 1×1 conv 投影到共享空间
        ↓
Few-shot Matching                 ← 在统一空间内做 prototype matching
```

### 中文解释与对我们的启示

| 模块 | 中文含义 | 在工业缺陷中的作用 | 对 CMPL 的启示 |
|---|---|---|---|
| **Low-level / Middle / High-level** | 多层级特征 | 不同粒度的 defect 表征 | YOLO26 backbone 默认只输出 final feature（P5）；如果用 P3+P4+P5 多尺度输入，prototype 会更鲁棒 |
| **Concat + Fusion** | 直接融合 | 简单但会破坏特征分布 | 这种 naive 拼接在 Few-shot 场景下尤其有害，因为少量 support 不足以纠正 misalignment |
| **Cross-stage Alignment** | 跨阶段对齐 | **核心**：让不同 stage 的特征先对齐，再融合 | 这是 Feature Pyramid Network (FPN) 的精神，但加了 explicit alignment loss |

### 可以借鉴的地方

1. **Multi-stage backbone 输出**：当前 YOLO26 我们只用最后一层（256 → 128）。可以改造为多尺度（如 stride 8, 16, 32），分别过 1×1 conv 到 128-d，再 concat。
   - **理由**：高光漆面 defect 尺度变化大（从麻点 ~10px 到划痕 ~500px），单尺度会丢失小目标。多尺度输入对 Few-shot 尤其重要 —— 因为 5 张 support 不足以让模型自动学到多尺度。

2. **Alignment loss**：在 prototype matching 之外，加一个 cross-stage alignment loss：让不同 stage 的 prototype 在共享空间中距离接近。
   - **理由**：这是 Few-shot 中防止 stage-specific bias 的有效正则化手段。我们的 `protonet_loop.py` 可以加一个新的 loss 项。

### 可以插入的地方（在我们代码中的具体位置）

```text
common/backbones.py                 ← ① 改造 YOLO26 编码器：返回 multi-stage features
   YOLO26Backbone.forward()         (当前只返回最后一层，可改为 dict of stages)

common/protonet_loop.py             ← ② 新增 calibrate_features() 函数
                                      (对 multi-stage 特征做 LayerNorm + projection)

common/maml_train.py                ← ③ 训练时加 alignment loss
   train()                          (新参数 align_loss_weight=0.1)
```

**理由总结**：Calibrated Feature Fusion 提示我们：**prototype 的质量瓶颈可能不在 support 数量，而在 feature space 的稳定性**。这是一个非常重要的反思 —— 我们一直在优化 prototype 算法（trim-mean, mahalanobis），但忽略了 backbone 输出本身是否稳定。如果多 stage 特征存在 systematic bias，再花哨的 prototype 也救不回来。这是一个低成本高回报的改进方向。

## 13.4 对 CMPL 的启发

Prototype 的质量不仅取决于：

```text
Support 数量
```

还取决于：

```text
Feature Space 是否稳定
```

因此可以考虑：

```text
Backbone
 ↓
Feature Alignment
 ↓
Prototype
 ↓
Query Matching
```

### 关键 Gap（研究空白）

| 维度 | 2024-2026 已有覆盖 | CMPL 的增量 |
|---|---|---|
| **Few-shot** | 充分 | 沿用 |
| **Cross-domain (单因素)** | 充分（光照/相机） | 沿用 |
| **Fine-grained defect** | 部分 | 加强 |
| **Foundation Model** | 充分 | 可选（YOLO26 已够用） |
| **Cross-component** | **几乎没有** | **核心创新点** |
| **Multi-condition + Cross-component 联合** | **几乎没有** | **核心创新点** |
| **RGB + 偏振 (Multimodal)** | **几乎没有** | **核心创新点** |

### 我们论文中的标准 Gap 表述

> "现有工作大多在 Few-shot × Cross-domain × Foundation Model 三者中取其二，但对 **Cross-component** 这一工业界最常见的实际场景考虑不足；更关键的是 **Multi-condition 与 Cross-component 同时变化**下的 defect-invariant representation 学习问题，目前缺乏系统研究。本文提出 CMPL，首次显式建模 Condition / Component / Defect 三种信息流的解耦表示，填补了这一空白。"

**理由总结**：这段文字（连同上面的图示）应该作为论文 Introduction 章节最后一段的标准模板。它做的事情是：
1. 指出已有工作的覆盖面（用表格/图示一目了然）
2. 指出空白（Cross-component + Multimodal）
3. 提出我们的 solution 占据空白
4. 形成 Gap → Solution 的标准论文写作节奏

# 18. 对你的 CMPL 最值得形成的理论框架

建议不要把：

> Component-aware

简单理解成：

```text
Component label
    ↓
Embedding                         ← 把 component 名（如"车门"/"引擎盖"）编码成向量
    ↓
Concat                            ← 直接拼接到 prototype 上
```

更好的理论分解是：

```text
Input Image                       ← 输入图像：含缺陷 + 工况 + 构件
     │
     ├───────────────┐             分叉到两条并行编码路径
     ↓               ↓
Condition        Component
Feature           Feature          ← 分别用专门编码器提取
     │               │
     ↓               ↓
Condition        Component
Encoder           Encoder          ← 编码器可以是 MLP、CNN 或注意力模块
     │               │
     └───────┬───────┘             汇合
             │
       Disentanglement              ← 解耦：通过对抗损失 / 正交约束让两条流尽量独立
             │
             ↓
    Defect-invariant Feature        ← 缺陷不变特征：去除 condition/component 后的"纯 defect"
             │
             ↓
      Prototype Learning              ← 原型学习：用这层不变特征做 Few-shot prototype
             │
             ↓
      Query Matching                  ← 查询匹配：新样本的特征与 prototype 比距离
             │
             ↓
        Detection                     ← 检测：输出 defect 类型 + 位置 + 置信度
```

### 中文解释（这是我们项目的核心图）

| 模块 | 中文含义 | 我们已实现 / 待实现 | 在项目中的对应代码 |
|---|---|---|---|
| **Input Image** | 输入图像 | ✅ RGB (+ 偏振预留) | `maml_train.py` 中的 `batch[0]['rgb']` |
| **Condition Feature / Encoder** | 工况特征 / 编码器 | 🟡 部分：aug_illumination 是一个轻量工况注入 | `episode_aug.py` 的 `IlluminationAug` |
| **Component Feature / Encoder** | 构件特征 / 编码器 | ❌ 待实现：当前没用 component label | 可以新增 `ComponentEncoder(nn.Module)` |
| **Disentanglement** | 解耦 | ❌ 待实现 | 需要一个 orthogonality loss |
| **Defect-invariant Feature** | 缺陷不变特征 | 🟡 部分：YOLO26 backbone 已经学过通用特征 | `common/multimodal_model.py` 的 `model.encode()` |
| **Prototype Learning** | 原型学习 | ✅ 已实现：ProtoNet + trim-mean + mahalanobis | `common/protonet_loop.py:build_prototypes()` |
| **Query Matching** | 查询匹配 | ✅ 已实现 | `common/protonet_loop.py:evaluate_protonet_query()` |
| **Detection** | 检测 | 🟡 只做 classification，未做 localization | 未来工作 |

### 这张图在论文中的位置

这张图是 **CMPL 论文的核心 Framework Figure**，应该出现在：
1. Introduction 末尾（问题定义后）
2. Method 章节首页（架构总览）
3. 每个消融实验的对照（指向图中具体模块开关）

### 当前实现 vs. 理论框架的差距

```text
已实现 (existence)        待实现 (gap)
─────────────────         ──────────────
✅ Prototype Learning     ❌ Disentanglement Loss
✅ Query Matching         ❌ Component Encoder
✅ Defect-invariant Feat  ❌ Condition Encoder (独立)
✅ Few-shot Recognition   🟡 Localization (输出只有 class)
```

**理由总结**：这张图不是简单的流程图，而是 **CMPL 论文的"主张图"**。它在视觉上说明：CMPL 不只是"另一种 ProtoNet"，而是一个**显式建模 Condition / Component / Defect 三种信息流的框架**。审稿人看到这张图，会立刻理解我们的科学问题（disentanglement）与技术贡献（独立的 Condition/Component 分支）。这是 CMPL 区别于 ProtoNet / RelationNet 的**最关键的视觉锚点**。

# 21. 因此 CMPL 可以进一步演化成

```text
              Multi-condition         ← 多工况输入：同一 defect 在不同光照 / 相机下采集
                    │
                    ↓
             Condition Encoder        ← 工况编码器：把 condition 信息提取为向量
                    │
                    ↓
              Condition-aware
                 Feature               ← 工况感知特征：显式表达"成像条件"
                    │
                    ×                  ← × 表示乘法或门控：Condition-aware Feature 反过来调节 backbone 输出
Input ─────→ Backbone ─────→ Fine-grained Feature
   ↑                              ↑    backbone 同时被 Condition 分支调节
   │                              │
   │                              ↓
   │                       Component Encoder       ← 构件编码器：识别当前是哪一种构件
   │                              │
   │                              ↓
   │                       Component-aware
   │                          Feature              ← 构件感知特征：显式表达"几何 / 外观"
   │                              │
   │                              ↓
   │                       Defect Representation    ← 三路特征融合后的缺陷表征
   │                              │
   │                              ↓
   │                       Prototype Learning        ← 用 defect rep 算 prototype
   │                              │
   │                              ↓
   │                       Adaptive Prototype        ← prototype 与 query 实时交互（论文七 EFINet）
   │                              │
   │                              ↕                  ← 双向流动（cross-attention）
   │                       Query Feature             ← 待测样本特征
   │                              │
   │                              ↓
   │                       Defect Detection          ← 输出 defect 类型 + 置信度
   ↓
(back to Input)
```

### 与上一节（第 18 节）的关系

| 章节 | 图 | 性质 |
|---|---|---|
| 第 18 节 | CMPL 理论框架 | **抽象理论图**（学位论文 / 论文 Intro 用）|
| 第 21 节 | CMPL 演进架构 | **具体工程图**（论文 Method 用）|

第 21 节加入了：
  - **Condition-aware Feature 通过门控（×）反向调节 Backbone**：体现 condition 不是静态特征，而是动态影响 backbone 行为
  - **Adaptive Prototype ↔ Query 双向流**：体现 prototype 会被 query 实时调整（EFINet 借鉴）
  - **多任务 Defect Detection**：未来可扩展到 segmentation / detection

### 中文解释与项目对应

| 模块 | 中文含义 | 已实现 | 项目代码位置 |
|---|---|---|---|
| **Multi-condition / Condition Encoder** | 多工况 + 编码器 | 🟡 aug_illumination 算一种 | `common/episode_aug.py:IlluminationAug` |
| **Condition-aware Feature (×)** | 工况门控 | ❌ | 需要新增 `nn.Linear` 把 condition feature 映射为 attention 权重 |
| **Input → Backbone → Fine-grained Feature** | 骨干编码 | ✅ | `common/backbones.py:YOLO26Backbone` |
| **Component Encoder / Component-aware Feature** | 构件编码器 | ❌ | 需要新增 `ComponentEncoder` 类 |
| **Defect Representation** | 缺陷融合表征 | 🟡 部分 | `common/multimodal_model.py:model.encode()` |
| **Prototype Learning / Adaptive Prototype** | 原型学习 + 自适应 | ✅ | `common/protonet_loop.py` |
| **Defect Detection** | 检测 | ✅ Classification / ❌ Localization | 当前只输出 class |

### 可以插入的地方（在我们代码中的具体位置）

```text

                                      (nn.Module 子类)

common/multimodal_model.py          ← ② 改造 forward：condition-aware gating
   CMPLModel.forward()               (在 backbone 输出上做 condition-feature 调制的 attention)

   build_prototypes()                (支持 cross-attention prototype)
```

第 22 节的 **Level 6**（CMPL 完整版）就是这张图的实现：

```text

         = CMPL
         + Condition-aware (×)
         + Component-aware
         + Fine-grained Feature

```

**理由总结**：第 21 节这张图是 **CMPL 论文的工程实现路线图**。它比第 18 节理论图更具体，可以直接对应到代码模块。对初学者来说，先看第 18 节理解"为什么"（motivation），再看第 21 节理解"怎么做"（implementation）。这种 **两阶段可视化** 是论文标准做法 —— Intro 给 abstract view，Method 给 concrete view。

# 28. 最终研究判断

从 2024–2026 的论文发展看：

```text
“Few-shot”
     ↓
已经不够新
```

真正越来越重要的是：

```text
Few-shot
    +
Domain Shift
    +
Generalization
    +
Foundation Model
    +
Real Industrial Conditions
```

而你现在的研究可以进一步把问题收敛为：

> **Cross-condition and cross-component few-shot industrial defect detection**

核心不是“如何用更复杂的网络检测缺陷”，而是：

> **如何让模型知道哪些变化来自工况/构件，哪些变化真正来自缺陷。**

如果这个问题通过实验得到充分验证，那么 CMPL 就不只是一个“新的 Meta-learning 网络”，而可以成为一个针对**工业跨域小样本缺陷检测中特定 representation entanglement 问题**的解决方案。
